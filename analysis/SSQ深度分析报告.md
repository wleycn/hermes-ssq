## 一、一句话结论

**这个项目的工程质量很高（代码结构、特征工程、6 套模型的抽象都很专业），但它在"用机器学习预测彩票"这个核心假设上是走不通的。** 我用 3487 期真实开奖数据做了客观统计检验，结论很明确：双色球开奖号码在统计上**不可预测**，现有模型学到的只是噪声/数据泄漏，而不是真实信号。

下面先用数据说话，再逐条给可落地的改进建议。

## 二、对历史数据的实证检验（可复现，纯标准库）

脚本：`analysis/empirical_check.py`，对 `ml/data/1.csv` 的 3487 期开奖数据：

| 检验项 | 结果 | 说明 |
|---|---|---|
| 红球号码频率 vs 均匀分布（卡方） | chi²=44.99 < 临界值46.19 | **不能拒绝"均匀分布"**——每个红球历史出现频率与理论期望无显著差异 |
| 蓝球号码频率 vs 均匀分布 | chi²=8.53 ≪ 25.0 | 同样无法拒绝均匀 |
| 和值序列自相关 lag1/lag5/lag20 | -0.004 / -0.029 / +0.041 | **≈0，无时间依赖**——上期开奖与下期毫无统计关联 |
| "最频繁6号"命中基线 | 平均重叠 1.107 | 与随机选6号的理论期望 **1.091** 无差异 |
| "近100期最频繁6号" | 平均重叠 1.129 | 同样无显著差异 |
| 头奖理论概率 | 1 / 17,721,088 | 红球 C(33,6)=1,107,568，乘蓝球16 |

**关键推论**：如果历史频率（冷热号、泊松、马尔可夫、遗漏……）真的含预测信号，那么"最频繁号码"的命中率应显著高于随机基线。实测三者几乎相同 → **这些数据特征不携带可预测的未来信息**。LSTM/CNN 在这些特征上训练，本质上是在对噪声建模（过拟合到训练集的随机波动）。

## 三、现有代码的 6 个关键缺陷（按严重度排序）

### 🔴 缺陷 1：把"已排序红球"当有序位置建模（最隐蔽的逻辑错误）
数据里 `Red1..Red6` 是**开奖后按大小排序**的（如 `[4,9,19,20,21,26]`）。这意味着：
- `Red1` 恒为最小值，`Red6` 恒为最大值，"位置"是排序的副产品，**没有真实物理含义**。
- 但 `rf_model` / `lgbm_model` 对每一列**单独训练一个分类器**（`--columns all` 跑 7 个模型），LSTM_REDS 也按 `pos0..pos5` 出 6 个分布。模型在学"最小值长什么样 / 最大值长什么样"这种确定性规则，而非在预测。
- 6 个位置分布的首位均值分别是 4.7 / 9.5 / 14.3 / 19.2 / 24.2 / 29.0——这是排序导致的**伪相关**，模型会"学会"却毫无预测价值。

### 🔴 缺陷 2：时间依赖为零，却用序列模型硬拟合
自相关 ≈0 已证明开奖无记忆性。但 LSTM 用 128 期窗口、CNN 用时间卷积去"捕捉时序规律"——它们在拟合**不存在的模式**，典型的数据窥探（data snooping）。

### 🟠 缺陷 3：评估指标在"筛掉稀有标签"后失真
`dataset.py` 和 `rf_model.py` 用 `min_label_count`（2~6）过滤稀有标签，又把 `top_k=6`。例：蓝球 16 个值若过滤掉几个，类别数降到 12，top-6 命中率**先天就有 50%**，这个指标失去意义，会给人一种"模型很准"的错觉。

### 🟠 缺陷 4：CNN_MATH 的后处理在用"未来信息做约束"
`cnn_model.predict_with_post_processing` 里：
- `Norm_Mean/Norm_Std`（红球和值的移动统计）在预测时取了 `df.iloc[-1]`——即**最新一期**的统计，再据此"校正"预测和值。这等于用当前期信息去约束对"下期"的预测，存在**轻微信息泄漏**。
- 泊松/熵阈值（4.0、10 等）是拍脑袋设的魔法数字，没有任何数据依据。

### 🟡 缺陷 5：模型从未做"对未来一期"的滚动验证（walk-forward）
现有评估是 `train_test_split` 随机切分。对时间序列，正确做法是**按时间滚动**：用第 1..k 期训练、预测第 k+1 期，逐期外推，统计真实命中率。随机切分会把未来数据泄露进训练集，虚高分数。

### 🟡 缺陷 6：特征工程有"重复/冗余"与轻微泄漏
- `feature_engineer.py` 约有 20 类特征、上百列，但很多高度共线（如 `Freq_*`、`Recent_Freq_*`、`LLN_Deviation_*` 都描述同一件事的不同窗口），会放大方差。
- `calc_onehot_features` 用 `shift(1)` 的上期号码做特征——这本身是合法的，但和"预测下期"混在同一张表里喂给某些窗口逻辑时，边界容易串期。

## 四、改进建议（分"正确认知"与"技术优化"两层）

### A. 先端正预期（最重要）
- 在 README 和所有输出里明确：**彩票是独立随机事件，任何模型都不能提高中奖概率**。本系统应定位为"统计学习 / 工程练手 / 历史数据可视化"项目，而非"选号神器"。
- 把现有"Top-K 概率"重新解释为**"历史上最像真实开奖的分布"**，而不是"最可能中奖的号码"。

### B. 如果仍想做"有意义"的预测研究，改这几点
1. **修正位置建模**：红球应作为**无序的 6 元组合**预测（multi-label / 集合预测），而非 6 个有序位置。或者直接输出每个号码(1-33)的出现概率（33 维 sigmoid），再取 top-6。
2. **改用 walk-forward 滚动验证**：实现 `rolling_predict(df, train_window, step)`，真实外推未来 N 期，报告真实命中率，与"随机选号基线"对比。若模型真实命中率不显著高于 1.091 的重叠基线，证明无效。
3. **用"随机森林特征重要性 / 置换重要性"验证信号**：如果所有 100+ 特征的重要性都≈均匀、且没有特征显著领先，就是"无信号"的客观证据——这比争论更有说服力。
4. **加一个"愚笨基线"对照**：历史最频繁 6 号、随机 6 号、均匀概率，三者的命中率都应作为模型的下限基准，写进评估报告。
5. **清理后处理泄漏**：CNN_MATH 的 `Norm_Mean` 约束改用**训练期统计**而非最新一期；魔法数字改成可配置并做敏感性分析。

### C. 工程层面（无论是否预测，都值得做）
- 锁定依赖：`requirements.txt` 标注精确版本（当前 numpy 2.4.6 / torch 2.13.0 等版本号过于"未来"，且未提供 `.venv`，新环境 `pip install` 可能装不上）。建议用 `pip freeze` 固化。
- 统一特征入口：RF/LGBM 用自己的 `calculate_all_features`，而 LSTM/CNN 用 `FeatureEngineer.compute_all_features`，**两套特征逻辑不一致**——同一个号码在不同模型里"看到"的特征不同，结果不可比。
- 删除 dead code：`.trae/documents` 里的清理计划提到要删 `cnn_1d/cnn_6_1`，但 `cnn_model.py` 目前**仍保留**这些类（我读到的版本里有 `_CNN1DNet`/`CNN6_1Model` 等），与 README "仅保留 6 条命令" 不一致，建议真正清理。
- 评估指标：**不要用 top-k + 过滤稀有标签的组合**，改用"完整类别 + 对数损失 + 滚动命中率"。
