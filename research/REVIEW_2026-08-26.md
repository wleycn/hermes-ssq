## 一、总体评价

项目整体架构**清晰、职责划分合理**：cron 三任务（抓开奖 / 发预测 / 月度重训）与 `jobs.json` 实测一致；模型层→`model_predictions`→均值集成→`select_numbers`→`predicted_picks` 的链路设计稳健；`model_predictions` 的 UPSERT 唯一约束（`run_at,model,ball_type,num`）正确且幂等；每模型独立取最新 `run_at` 的集成方式避免了跨模型 run_at 耦合；`1.csv` 作为唯一权威数据源 + 尾部查重追加是稳妥的。科学立场（诚实标注"随机过程不可突破"、conformal/shrinkage 仅作解释层）也值得肯定。

但**文档与实现严重脱节**，这是本次审查的核心问题。两份"权威文档"仍在描述 2026-08-22 之前的设计，而代码在 2026-08-23（脚本归一）和 2026-08-26（db_draw 拍板）已发生改变，最严重的是 **H1 决策（draw_history 只读归档 / 手动同步）已被代码实际推翻**，但文档未更新且仍在声明该不变量。此外存在**凭证硬编码并随代码推送到 github/gitee** 这一安全/文档双重问题。以下按严重度列出。

## 二、HIGH 级问题

### H1【文档准确性·核心】draw_history 已被代码自动写入，但文档仍声明"只读归档 / 手动同步 / update_ssq.py 不写 PG"

- **证据**
  - `update_ssq.py:290-300`：每轮开奖抓取后调用 `db_draw.upsert_draw(conn, rec)` 写 `ssq.draw_history`，且注释"写库 ssq.draw_history（幂等 upsert，失败不影响 CSV 入库）"。
  - `ml/data/db_draw.py:5` 模块 docstring 明确："职责（Rocky 2026-08-26 拍板）：开奖获取 → 写 CSV → 写 ssq.draw_history → 从本表读最新 → 发邮件"。
  - 但文档声称相反：
    - `ARCHITECTURE.md:45`（§1.2 cron 表）："draw_history 不自动同步（**update_ssq.py 不写 PG**，需另行 pg_schema.py 手动同步，2026-08-16 doc 审核 H1）"
    - `README.md:185`："1.csv 经 update_ssq 更新后，需重跑 pg_schema.py 同步"
    - `README.md:373`："draw_history … 只读归档，默认不自动同步（手动跑 pg_schema.py 才更新），所以**可能比 1.csv 旧**。设计上故意如此（见 H1 决策）"
    - `pg_schema.py:149-150,173-177` 的 `draw_history_drift` / `sync_draw_history` 注释仍写"H1 决策：draw_history 为只读归档，由 import_draw_history 手动同步；不进生产 cron"。
- **问题实质**
  1. **文档描述了一个已不存在的完整性不变量**。当前每个开奖日 22:00，生产路径（cron `246a519bce0b` → `update_ssq.py`）都会主动写 `draw_history`。这恰好推翻了 H1 的核心目的——"防止自动链路把脏数据写进权威归档"。
  2. **出现了两条互相独立的写入路径**：①`update_ssq.py` 增量 `DELETE+INSERT` 单期（`db_draw.upsert_draw`）；②`pg_schema.import_draw_history` 是 `DELETE FROM ssq.draw_history;` 整表清空后全量重导（`pg_schema.py:95`）。两者语义不同、无协调，文档却只承认第②条。
  3. **"draw_history 可能比 1.csv 旧"的论断现在来源错了**。当前若 `update_ssq.py` 的 PG 写入因异常失败，会被 `update_ssq.py:299-300` 吞掉（"不影响 CSV/发信"），导致 PG 落后 CSV——这正是"滞后"的真实成因，而非文档所说"手动同步从未跑过"。
- **改进建议**
  - 二选一，并让文档与代码一致：
    - **方案 A（推荐，恢复 H1 语义）**：`update_ssq.py` 只写 `1.csv`，**不**写 `draw_history`；`draw_history` 仍由 `pg_schema.py` 手动/运维同步。恢复"只读归档"不变量，消除双写路径。
    - **方案 B（承认新设计）**：保留自动同步，但必须**删除 H1 相关所有声明**（ARCHITECTURE §1.2 注释、README §4/术语表、pg_schema 注释），并明确"draw_history 由开奖 cron 自动增量同步，pg_schema 仅用于全量重建"。
  - 无论选哪个，都应消除双写路径：若选 B，应让 `pg_schema.import_draw_history` 走"增量 upsert from 1.csv"而非"DELETE 全表"，避免与增量写入冲突。
  - 当前实测：1.csv 与 draw_history 均为 3494 行、末期为 2026098（2026-08-25），**暂时一致**——但这是依赖"两次写入都成功"的脆弱一致，不是设计保证。

### H2【文档准确性 + 安全】PROJECT.md 称"PG 走 .env DATABASE_URL，不硬编码"，但全部代码硬编码，且密码已随代码推送到 github/gitee

- **证据**
  - `PROJECT.md:38`："- PG 连接走 `.env` 的 `DATABASE_URL`，不硬编码"
  - 实测硬编码 `password="hermes123"` 的文件（均为生产路径）：`batch_predict_pg.py:43`、`pg_schema.py:23`、`select_numbers.py:46`、`reconcile_picks.py:20`、`retrain_pipeline.py:37`、`ssq_send_picks.py:199`（DSN 串形式）、`ml/data/db_draw.py:14`，外加 `analysis/`、`_verify/` 多个脚本。
  - 实测 `.env` 的 `DATABASE_URL` 密码 = `hermes123`（base64 解码 `aGVybWVzMTIz` → `hermes123`），**与代码硬编码值一致**——所以不存在"运行时连不上"的故障，问题纯在策略/文档层面。
  - `git remote -v` 显示推送目标：`github.com:wleycn/hermes-ssq.git` 与 `gitee.com:aquawork/hermes-ssq.git`；`git ls-files` 确认上述含密码的源文件**已被 git 跟踪**（`.gitignore` 只忽略了 `.env` 和 `.hermes/`，并未忽略这些 .py）。即 `hermes123` 已随源码进入 git 历史并推送到远端。
- **问题实质**
  1. **文档与实现直接矛盾**：PROJECT.md 声明的凭证策略在项目里从未被遵守。
  2. **凭证进入版本库/远端**：即便本机 PG 是 localhost-only、内部 URL 不算敏感（ARCHITECTURE 2026-08-23 已据此"接受"硬编码），把数据库密码写进会被 push 到 github/gitee 的源文件仍是不良实践；一旦任一远程仓库公开，localhost 端口若被暴露或未来迁移到非本机，该密码即成泄漏点。且 git 历史清除成本高。
- **改进建议**
  - 短期务实方案（符合"内部 URL 不算敏感"的既定基调，同时消弭文档矛盾）：统一从 `.env` 的 `DATABASE_URL` 解析 `psycopg.connect(os.environ["DATABASE_URL"])`，删除所有硬编码副本；并**同步修订 PROJECT.md:38** 为真实做法（"凭证在 .env；代码从 DATABASE_URL 读取"或"本地 PG 密码以常量集中在一处 `db.py` 并明确不推送"）。
  - 至少把 `PG` 连接字典抽到一个**被 gitignore 的本地模块**或统一 `db.py`，避免 8+ 处散落、且方便将来轮换。
  - 即便保留硬编码，也应在 README/PROJECT 明确"本仓库含本地 PG 密码，请勿设为 public"——而不是声称"走 .env 不硬编码"。

## 三、MEDIUM 级问题

### M1【数据库使用】model_predictions "30 天保留"是文档政策，但**没有任何定时任务执行清理**

- **证据**
  - `ARCHITECTURE.md:74`（§1.4）："保留策略：model_predictions 30 天；draw_history 全量（绝不清理）"
  - `README.md:168,178-183`：表保留策略 + `cleanup_predictions.py`（默认 dry-run，`--confirm` 才删）。
  - 实测 `jobs.json` 仅 3 个 Hermes 任务（`246a519bce0b`/`ced57f0994d8`/`98164fe6c0d6`），系统 crontab 仅 `run_research.py`；**没有任何任务调用 `cleanup_predictions.py`**。`cleanup_predictions.py` 的删除逻辑需要人工显式 `--confirm`。
  - 实测 `model_predictions` 当前 588 行，且 `data_date` **全部为 2026-08-22**（run_at 范围 2026-08-22 10:29–15:18，即 2 个批次），证明月度重训是唯一写入源，且从未经自动清理。
- **问题实质**：保留策略只是"代码里存在、需人工触发"，并非运行中的策略。当前因只由月度重训写、规模仅数百行，实际无害；但若将来 `batch_predict_pg.py` 被更频繁调用（或有人手动跑），表会无界增长，而文档给人的印象是"已自动保留 30 天"。
- **改进建议**：把 `cleanup_predictions.py --confirm` 挂进月度重训 cron（`98164fe6c0d6`）的收尾，或单独建一个低频 cron（如每日/每周）。并在文档明确"保留由 X cron 强制执行"。

### M2【架构/数据库】双写入路径 + 被吞掉的异常 → draw_history 与 1.csv 可静默漂移

- **证据**：`update_ssq.py:290-300` 写 PG 失败时 `except` 仅打印 `[warn]` 并继续；`db_draw.upsert_draw`（`ml/data/db_draw.py:24-44`）是"先 DELETE 再 INSERT"两步、中间 `conn.commit()`，若两步之间进程中断会丢该行。另见 H1 的 `pg_schema.import_draw_history` 整表清空式重导。
- **问题实质**：H1 新设计让"生产链路"也能动归档表，且写入失败被静默吞掉，使"PG 落后 CSV"从"理论上不会发生"变成"运行时会偶尔发生且无人知晓"。文档把滞后归因于"手动同步未跑"，掩盖了真实故障模式。
- **改进建议**：①失败不应静默吞掉，至少记到 cron 日志并告警；②upsert 改为单条 `ON CONFLICT DO UPDATE`（与 `model_predictions` 一致），保证原子性；③见 H1 消除双写。

### M3【文档/逻辑自洽】select_numbers 仍基于"draw_history 滞后"假设只读 1.csv，注释已陈旧

- **证据**：`select_numbers.py:161-162,180-181`（`build_conformal`）："开奖号取 **1.csv**(生产数据源, 永远最新) 而非 draw_history(只读归档, H1 决策下**可能滞后**)"。该前提（draw_history 滞后）在当前自动同步设计下不再成立。
- **问题实质**：逻辑本身没错（读 1.csv 也安全），但代码注释与当前架构自相矛盾，会误导后续维护者。属于文档-代码反向不一致（代码注释在描述一个已被推翻的旧设计）。
- **改进建议**：随 H1 的定案，统一修正相关注释（draw_history 是否与 1.csv 同步、conformal 为何读 1.csv）。

## 四、LOW 级问题

- **L1 连接管理**：无连接池，每次运行新建连接；`update_ssq.py` 单次运行开 2 个连接（写 draw_history、读 latest），`select_numbers.main()` 开 2 个（主 + conformal）。对 cron 低频负载可接受，但建议抽统一 `get_conn()` 并考虑 `psycopg.ClientPool` 以便日后高频复用。
- **L2 `db_draw.upsert_draw` 非原子**：`DELETE + INSERT` 两步提交，非真正 UPSERT，崩溃会丢行。建议改用 `ON CONFLICT DO UPDATE`（draw_history 可建唯一约束 `dNum`）。
- **L3 `draw_history.dNum` 为 `CHAR(7)`**：当前期号 2026098（7 位）刚好；跨入 8 位期号年代后 `CHAR(7)` 会静默截断/报错。建议改 `VARCHAR(8)` 或 `INT` 主键。
- **L4 `select_numbers.py:48` `MODELS` 冗余硬编码**：与 `batch_predict_pg.MODELS` 重复，注释自承"生产以 batch_predict_pg.MODELS 为准"，存在漂移风险。建议导入而非重定义。
- **L5 `retrain_pipeline.py:40` 经 `scripts/ssq_send_picks.py` 壳中转**：归一后"真身"已在项目根 `ssq_send_picks.py`，retrain 仍通过 `~/.hermes/scripts/` 壳二次跳转（壳→真身）。功能正常，但与"改真身即生效"原则略有出入，建议直调项目根真身。
- **L6 `pg_schema.EXPECTED_ROWS = 3488` 陈旧**：实际 3494，仅影响 `__main__` 打印的期望值，不影响逻辑，但属文档式 stale 常量。
- **L7 文档"3492 期"过时**：ARCHITECTURE/README 多处写"3492 期"，实测 1.csv 与 draw_history 均为 3494（末期 2026098 / 2026-08-25）。属数据增长导致的轻微文档滞后。
- **L8 cron `98164fe6c0d8` 实际为 skill 包装**：`jobs.json` 中 `98164fe6c0d6` 的 `skill=ssq-lottery-pipeline`、`script=None`，而 ARCHITECTURE:47 写"retrain_pipeline.py --no-email"。实为 skill 内部调脚本，措辞可更精确（非缺陷）。

## 五、架构合理之处（证明非只挑刺）

1. **Cron 职责划分清晰且与配置一致**：`jobs.json` 实测三任务（开奖检查 `246a519bce0b` no_agent 跑 update_ssq；发预测 `ced57f0994d8`、月度重训 `98164fe6c0d6` 均 pin 到 `tencent/hy3:free` 走 ssq-lottery-pipeline skill）与 ARCHITECTURE §1.2 完全吻合；agent cron 已 pin 模型，规避了 config-drift 静默跳过的历史坑。
2. **模型层→集成链路设计稳健**：`model_predictions` 唯一约束 `(run_at,model,ball_type,num)` + `ON CONFLICT DO UPDATE SET prob=EXCLUDED.prob`（`batch_predict_pg.py:153-163`）正确幂等；`select_numbers.load_latest_probs` 每模型每球种独立取 `MAX(run_at)`，避免"必须同一次 run 共享 run_at"的耦合，工程上更松耦合。
3. **单一权威数据源 + 幂等追加**：`1.csv` 为唯一权威，`append_ssq.append_records` 尾部 100 行查重 + 单期幂等，CRLF 保真，重复运行不污染。
4. **时区处理 thoughtful**：`data_date` 由 Python 侧北京日期写入、并在 `pg_schema` 把列 DEFAULT 也改为 `Asia/Shanghai`，规避了 PG `Etc/UTC` 的 8 小时偏差（文档与代码一致）。
5. **科学诚实立场**：conformal / James-Stein shrinkage 明确"仅风险分层/概率诚实化，不提升命中率"；探针体系定位"检验器非预测器"。这在彩票类项目里是难得的纪律。
6. **shell-wrapper 归一落地正确**：实测 `scripts/update_ssq.py` 壳正确 `subprocess` 调项目真身、`cwd=真身目录`、不 capture stdout（保留 cron 日志）；4 脚本均已转壳，旧副本 `.bak_20260823` 备份，符合 ARCHITECTURE 2026-08-23 决策。
7. **复盘表幂等**：`ssq_send_picks.db_upsert` 按 `(period,mode,group_idx)` 先删后插，重跑安全；`predicted_picks` 有 `idx_predicted_picks_period` 索引，复盘查询高效。

## 六、结论与优先修复建议

- **最该先修（HIGH）**：H1（draw_history 自动写入 vs 文档"只读/手动同步"）——要么恢复只读归档不变量，要么正式采纳自动同步并全面改写文档；H2（PROJECT.md 与代码凭证策略矛盾 + 密码进 git 远端）——统一从 `.env` 读取并修正文档，或至少如实声明。
- **其次（MEDIUM）**：M1 给 30 天保留策略加定时执行；M2 消除双写路径与静默异常；M3 清理"draw_history 滞后"陈旧注释。
- **LOW 可顺手清**：L1–L8 多为一致性/健壮性小项，可在下次改动时一并处理。
- **总体**：架构骨架健康、科学立场端正；主要风险集中在"文档未随 2026-08-23/26 两次改造更新"以及"凭证管理口是心非"。修复成本很低（多为文档+少量重构），建议本周内闭环 H1/H2。
